System Design of a Shipping & Logistics ERP Platform

A practical system-design case study based on my enterprise ERP project experience, covering requirements, data model, APIs, architecture, permission flow, bottlenecks and optimisation.

Functional requirement

1) Users should be able to access only the ERP menus and documents permitted to them.

2) Users should be able to work across shipping, finance/accounting and HR/payroll modules.

3) Users should be able to search, filter and retrieve operational records.

4) Users should be able to view and manage business documents through DMS-related workflows.

5) The platform should support reporting and module-specific business workflows.

Non functional Requirement

1) High availability with minimal latency for common ERP operations.

2) Secure, permission-aware access to menus, documents and APIs.

3) Scalable enough to support a large enterprise application surface.

4) Maintainable code and deployment environments across many modules.

5) Reliable data access and predictable performance for reporting workloads.

My resume describes the platform as spanning 160+ feature modules across Shipping Operations, Finance & Accounting, and HR & Payroll.

Back of the Envelope Estimation

The resume does not provide production traffic, concurrent users or database-size numbers. Instead of inventing those numbers, I use a capacity-planning model that can be filled with real production metrics.

Peak RPS=Daily API requests × peak factor ÷ 86,400
Storage growth=Documents/day × average size × retention period
DB capacity=Operational data + indexes + replication overhead

For an enterprise ERP, read-heavy reporting endpoints and document traffic should be measured separately from transactional APIs.

Bottleneck

At this scale, the likely pressure points are not one single API but the interaction between many modules, shared database workloads, report queries, document traffic and repeated permission checks.

Large module surface

More modules increase coupling and release complexity.

Database-heavy reports

Large filtered queries can compete with transactional traffic.

Document traffic

Large files should avoid unnecessary application-server transfer.

Permission lookup

Repeated authorization checks can add latency.

Optimisation

  1. Indexing: add PostgreSQL indexes for common filters, joins and sort keys.
  2. Pagination: never load large report/result sets into the browser at once.
  3. Caching: cache stable menu/permission metadata where safe.
  4. Object storage: keep large documents outside the transactional database.
  5. Async work: move long-running jobs to background processing.
  6. Containerisation: keep environments consistent with Docker.
  7. Observability: add logs, health checks and metrics around critical APIs.
  8. Domain separation: keep module boundaries clear so changes are easier to deploy.
